Business requirements guide the solution architecture. Application, platform, and data design converge in the event-driven system. Security, observability, and reliability support its operation in production.

Business requirementsGoals, constraints & service levels

Define success criteria

Turn business goals into measurable requirements. Agree on expected traffic, acceptable latency, availability targets, and compliance constraints before choosing technologies.

Solution architectureBoundaries & trade-offs

Connect requirements to design

Define system boundaries and document the trade-offs. Use those decisions to align service contracts, cloud infrastructure, and data ownership.

ApplicationJava & Go services

Define service responsibilities

Group behavior by business capability. Give Java and Go services clear API and event contracts so teams can change and deploy each service independently.

PlatformAWS & Google Cloud

Choose where workloads run

Choose compute, network boundaries, and managed services on AWS or Google Cloud based on availability, scaling, and operational requirements.

DataSQL & NoSQL

Assign data ownership

Choose SQL or NoSQL storage around access patterns and consistency needs. Define who owns each dataset and how it will be backed up and restored.

Event-driven systemKafka or Google Cloud Pub/Sub

Decouple producers and consumers

Publish business changes through Kafka or Pub/Sub. Agree on schemas and ordering guarantees, and make consumers safe to retry or replay.

Production foundationsSecurity, observability & reliability

Build in operational safeguards

Limit access with least privilege, collect logs, metrics, and traces across boundaries, and use service-level objectives to guide alerting and recovery tests.

Production platformDeployment & operations

Release and operate the system

Deploy workloads through a repeatable pipeline. Verify rollout health, document rollback steps, and test restoration against recovery targets.

Read the enterprise design notes

Follow how a request becomes an event and how services recover from failures. This reference model describes general design choices.

API boundary

Validate requests, authorize callers, and define each operation’s contract before passing work to the application layer.

Event contract

Publish changes using an explicit event schema. Define the fields consumers depend on, how the schema evolves, and where ordering matters.

Consumer

Use a stable idempotency key. Make processing safe to retry and isolate failures before a backlog affects unrelated work.

Operations

Trace work across boundaries, track latency and failures, and review recovery against service-level objectives.
